# Лабораторна робота 4. Відповіді

## Частина 1

### Inode

Номер inode, розмір, Links, права і власник `a.txt`:
- **Inode:** `1095710`
- **Розмір:** `6` байтів
- **Links:** `1`
- **Права:** `0644` (`-rw-r--r--`)
- **Власник:** `Uid: 1000 (codespace)`, `Gid: 1000 (codespace)`

Що таке `.` і `..`:
- `.` (inode `1095706`) — жорстке посилання на поточний каталог (`play`).
- `..` (inode `1095582`) — жорстке посилання на батьківський каталог (`lab4`).

### Жорсткі посилання

Що спільного в `a.txt` і `b.txt` після `ln`, що змінилося в Links:
- Спільне: однаковий номер inode (`1095710`), тип файлу, розмір, права, власник, часові мітки та вміст (допис `again` у `b.txt` одразу видно при читанні `a.txt`).
- Лічильник `Links` збільшився з `1` до `2`. Вивід `stat` для обох імен повністю ідентичний, окрім поля `File:` (самого імені).

Чи може ім'я зберігатися в inode, де воно зберігається і звідки `stat` його бере:
- Ні, ім'я не зберігається в inode, оскільки на один inode може вказувати багато різних імен.
- Імена зберігаються у записах каталогу (directory entries) у вигляді пар `(ім'я -> номер inode)`.
- Команда `stat` бере ім'я з аргументу командного рядка, за яким знаходить відповідний запис у каталозі та зчитує метадані з вказаного там inode.

Яке з двох імен основне:
- Жодне — обидва імені є рівноправними жорсткими посиланнями на один і той самий inode.

Що зробив `rm`:
- `rm a.txt` видалив запис `a.txt` із каталогу та зменшив лічильник посилань `Links` в inode `1095710` з `2` до `1`. Сам файл (inode та блоки даних) не видалився і залишився доступним через `b.txt`.

Помилки двох команд `ln` і їхні причини:
- `ln sub sub-link` → `ln: sub: hard link not allowed for directory` — операційна система забороняє створювати жорсткі посилання на каталоги, щоб уникнути утворення циклів у дереві каталогів.
- `ln b.txt /dev/shm/b.txt` → `ln: failed to create hard link '/dev/shm/b.txt' => 'b.txt': Invalid cross-device link` — поточний каталог розташований на файловій системі `overlay`, а `/dev/shm` — на окремій ФС `tmpfs`. Номери inode унікальні лише в межах однієї файлової системи, тому жорсткі посилання між різними ФС неможливі.

### Символьні посилання

Чи той самий inode в `c.txt` і `b.txt`, чому такий розмір `c.txt`:
- Ні, номери inode різні: `b.txt` має inode `1095710`, а `c.txt` — власний inode `1095712` (тип `l` — символьне посилання).
- Розмір `c.txt` дорівнює `5` байтам, оскільки вмістом символьного посилання є текстовий рядок цільового шляху `b.txt` (довжина якого становить 5 символів).

Що сталося з `c.txt` після `mv` і після створення нового `b.txt`:
- Після `mv b.txt d.txt` посилання `c.txt` стало «битим» (dangling), оскільки файлу з ім'ям `b.txt` у каталозі не залишилося (`cat c.txt` видав `No such file or directory`).
- Після створення нового файлу `b.txt` (з новим inode `1095713` і вмістом `new`) символьне посилання `c.txt` почало вказувати на цей новий файл (вивело `new`), бо символьне посилання розв'язується за текстовим шляхом, а не за номером inode.

### Відкритий файл і `rm`

Вивід `ls -l /proc/.../fd` і `cat /proc/.../fd/N`:
```text
total 0
lrwx------ 1 codespace codespace 64 Nov 23 16:24 0 -> /dev/pts/0
lrwx------ 1 codespace codespace 64 Nov 23 16:24 1 -> /dev/pts/0
lrwx------ 1 codespace codespace 64 Nov 23 16:24 2 -> /dev/pts/0
lrwx------ 1 codespace codespace 64 Nov 23 16:24 27 -> /dev/pts/ptmx
lr-x------ 1 codespace codespace 64 Nov 23 16:24 3 -> '/home/codespace/lab4/play/gone.txt (deleted)'
```
`cat /proc/$(pgrep -n tail)/fd/3`:
```text
still here
```

Чи видалено файл після `rm`, чому дані ще можна прочитати, коли ядро звільнить місце:
- Після `rm` зникло лише ім'я файлу з каталогу (лічильник посилань в inode став `0`), але сам файл ще не видалено.
- Дані ще можна прочитати через `/proc/.../fd/3`, оскільки процес `tail` утримує відкритий файловий дескриптор цього файлу (лічильник відкритих посилань в ядрі > 0).
- Ядро остаточно звільнить inode та блоки даних на диску лише тоді, коли лічильник жорстких посилань дорівнює 0 **і** закрито всі відкриті файлові дескриптори (тобто після завершення `tail` по `Ctrl+C`).

## Частина 3

### Наївна заміна

Що лежить у `cfg` після переривання на `truncated`:
- Файл `cfg` порожній (`0` байтів), оскільки прапорець `O_TRUNC` у системному виклику `open` миттєво обрізав старий вміст `v1` до нуля ще до того, як програма почала записувати `v2`.

### Безпечна заміна

Вивід `strace`:
```text
openat(AT_FDCWD, "/etc/ld.so.cache", O_RDONLY|O_CLOEXEC) = 3
close(3)                                = 0
openat(AT_FDCWD, "/lib/x86_64-linux-gnu/libc.so.6", O_RDONLY|O_CLOEXEC) = 3
close(3)                                = 0
openat(AT_FDCWD, "cfg.tmp", O_WRONLY|O_CREAT|O_TRUNC, 0666) = 3
write(3, "v2\n", 3)                     = 3
fsync(3)                                = 0
close(3)                                = 0
rename("cfg.tmp", "cfg")                = 0
openat(AT_FDCWD, ".", O_RDONLY|O_DIRECTORY) = 3
fsync(3)                                = 0
close(3)                                = 0
write(2, "saved 3 bytes to cfg\n", 21saved 3 bytes to cfg
)  = 21
+++ exited with 0 +++
```

Чи збігається послідовність викликів із кроками з «Дано»:
- Так, повністю збігається: створення/відкриття тимчасового файлу `cfg.tmp`, запис усіх даних (`write`), синхронізація даних на диск (`fsync`), закриття дескриптора (`close`), атомарне перейменування (`rename`) поверх `cfg`, а також відкриття батьківського каталогу (`.`) та виклик `fsync` для нього.

Чи змінився номер inode і чому:
- Так, номер inode змінився з `1441882` на `1441883`, оскільки `cfg.tmp` було створено як новий окремий файл зі своїм inode, а системний виклик `rename` переприв'язав ім'я `cfg` до inode нового файлу та видалив старе посилання.

### Що лишається після збою

| Контрольна точка | `cfg` | `cfg.tmp` | Якщо вимкнути живлення |
| ---------------- | ----- | --------- | -------------------- |
| `created`        | `v1`  | Порожній (`0` байтів) | `v1` (оригінальний `cfg` не чіпали, `rename` не викликався; на диску лишиться `v1` і, можливо, порожній `cfg.tmp`) |
| `written`        | `v1`  | `v2`      | `v1` (`cfg` не змінювався; дані `cfg.tmp` ще могли не скинутися з page cache на диск, але `cfg` містить повну версію `v1`) |
| `synced`         | `v1`  | `v2`      | `v1` (дані `cfg.tmp` вже на диску після `fsync`, але `rename` ще не виконано, тому `cfg` досі вказує на `v1`) |
| `renamed`        | `v2`  | Немає (`No such file or directory`) | `v1` або `v2` (`rename` атомарно виконано в пам'яті, але зміни каталогу ще не зафіксовані на диску через `fsync` каталогу; в ext4 після перезавантаження буде або повністю стара `v1`, або повністю нова `v2`, без пошкодженого вмісту) |
| `dir-synced`     | `v2`  | Немає (`No such file or directory`) | `v2` (і дані нового файлу, і запис каталогу після `rename` гарантовано синхронізовані з диском через `fsync`) |

### Помилка запису

Вивід `safe`, код завершення, `ls -l` і `cat` після нього:
```text
write: No space left on device
safe:1
total 4
-rw-r--r-- 1 codespace codespace 4 Nov 23 16:29 cfg
cfg:old
```
Програма вивела помилку `write: No space left on device`, повернула код завершення `1`, видалила тимчасовий файл `cfg.tmp` і зберегла оригінальний файл `cfg` зі старим вмістом `old` (розміром 4 байти).

Що сталося з `cfg` у наївному способі:
```text
write: No space left on device
naive:1
total 1024
-rw-r--r-- 1 codespace codespace 1048576 Nov 23 16:29 cfg
```
У наївному способі `open` із прапорцем `O_TRUNC` одразу знищив старий вміст `old`, після чого `write` встиг записати лише `1048576` байтів (1 МіБ) нулів до вичерпання місця на ФС і завершився з помилкою `No space left on device` (код `1`). В результаті файл `cfg` виявився пошкодженим — перезаписаним обрізаними даними.
