# Частина 1. Inode і посилання

Тема: файли, каталоги, посилання. Інформація: OSTEP [39. Interlude: Files and Directories](https://pages.cs.wisc.edu/~remzi/OSTEP/file-intro.pdf) (розділи про `stat`, жорсткі й символьні посилання).

## Мета

З'ясувати, що таке inode і де зберігається ім'я файлу, чим жорстке посилання відрізняється від символьного і коли ядро справді видаляє файл.

## Дано

Лише команди. Виконуйте їх в окремому каталозі:

```sh
cd ~/lab4/part1-links
mkdir play
cd play
```

- `stat FILE` — номер inode, тип, розмір, кількість посилань (Links), права, власник, часові мітки файлу.
- `ls -i` — номер inode перед кожним ім'ям; `ls -li` — те саме разом з `ls -l`.
- `ln TARGET LINK_NAME` — жорстке посилання, `ln -s TARGET LINK_NAME` — символьне.
- `df -T PATH` — на якій файловій системі і якого типу лежить шлях.

## Завдання

1. **Inode.**

   ```sh
   echo hello > a.txt
   stat a.txt
   ls -lia
   ```

   Запишіть номер inode, розмір, Links, права і власника `a.txt`. Що таке `.` і `..` у виводі `ls -lia`?

2. **Жорсткі посилання.**

   ```sh
   ln a.txt b.txt
   ls -li
   stat a.txt b.txt
   echo again >> b.txt
   cat a.txt
   rm a.txt
   ls -li
   cat b.txt
   ```

   Що спільного в `a.txt` і `b.txt` після `ln`, і що змінилося в Links? Порівняйте вивід `stat` для двох імен. Чи може ім'я зберігатися в inode? Де воно зберігається і звідки `stat` його бере? Яке з двох імен основне? Що зробив `rm`?

   ```sh
   mkdir sub
   ln sub sub-link
   ln b.txt /dev/shm/b.txt
   df -T . /dev/shm
   ```

   Яку помилку дає кожна з двох команд `ln` і чому?

3. **Символьні посилання.**

   ```sh
   ln -s b.txt c.txt
   ls -li
   mv b.txt d.txt
   cat c.txt
   echo new > b.txt
   cat c.txt
   ls -li
   ```

   Чи той самий inode в `c.txt` і `b.txt`? Чому розмір `c.txt` саме такий? Що сталося з `c.txt` після `mv` і після створення нового `b.txt`?

4. **Відкритий файл і `rm`.** Знадобляться два термінали (два вікна або дві вкладки, у кожній — `vagrant ssh` або вхід у VM), обидва в каталозі `play`.

   У першому терміналі створіть файл і відкрийте його через `tail -f`: `tail` покаже вміст і чекатиме нових рядків, доки ви не натиснете Ctrl+C.

   ```sh
   echo 'still here' > gone.txt
   tail -f gone.txt
   ```

   У другому терміналі:

   ```sh
   rm gone.txt
   ls
   ls -l /proc/$(pgrep -n tail)/fd
   ```

   Остання команда показує відкриті дескриптори процесу `tail`. Знайдіть рядок з `gone.txt` і прочитайте файл через його номер `N`, підставивши число замість `N`:

   ```sh
   cat /proc/$(pgrep -n tail)/fd/N
   ```

   Потім натисніть Ctrl+C у першому терміналі і подивіться, чи лишився процес: `pgrep -n tail`.

   Чи видалено файл після `rm`? Чому дані ще можна прочитати? Коли ядро звільнить місце на диску?
